# Gitea 业务交付版部署手册

本版直接修改 limluo/gitea 的 Go 服务、数据库模型、Actions 密钥分发及页面模板。登录 Gitea 后选择顶部「业务工作台」，进入仓库完成审批与发版。原生仓库和管理页面仍可使用。

## 使用 Linux amd64 二进制包

在全新的 x86_64 Linux 试点机安装 Git、Git LFS、CA 证书和 systemd，解压部署包并进入其目录。程序内置前端和模板。以下命令以 root 运行，默认新建服务监听 3000 端口，请确保端口可用。

```sh
getent passwd git >/dev/null || useradd --system --create-home --shell /bin/bash git
install -d -o git -g git /var/lib/gitea-business/custom/conf
chown git:git /var/lib/gitea-business /var/lib/gitea-business/custom
install -m 0755 gitea-business-linux-amd64 /usr/local/bin/gitea-business
install -m 0644 gitea-business.service /etc/systemd/system/gitea-business.service
systemctl daemon-reload
systemctl enable --now gitea-business
journalctl -u gitea-business -n 50
```

在浏览器访问服务端 3000 端口，完成 Gitea 安装向导。预研可选择 SQLite。选择仓库根目录时请确保 git 用户可写。Git HTTP 可直接使用，Git SSH 需按原生 Gitea 文档配置系统 sshd 或启用内置 SSH 服务。

## 从源码构建容器

源码基线为 fork 的 main 提交 b1a6cdadc83ebf4a33a69af8d457cc7f623f2d22。源码包使用仓库自带的多阶段 Dockerfile，需要 Linux Docker、Compose、BuildKit 及访问镜像和构建依赖的网络。

解压完整源码包，在源码根目录运行以下命令。

```sh
# GitHub 源码归档不带 .git，原生 Dockerfile 在编译阶段会挂载此目录。
test -d .git || git init -q
docker compose -f contrib/business-delivery/compose.yml up -d --build
docker compose -f contrib/business-delivery/compose.yml logs -f gitea
```

访问服务器 3000 端口，按安装向导选择数据库并创建首个管理员。Compose 默认使用独立数据卷，适合新建试点。已有实例请先复制数据库、仓库、附件、Actions 数据、app.ini 与原有 SECRET_KEY，用副本验证升级。源码基线比手册示例 1.22.6 更新，数据库升级后回退需要还原同一时点的数据备份。面向用户时按原生 Gitea 方式配置 ROOT_URL、TLS 和反向代理。

## 配置试点

1. 管理员在业务工作台初始化仓库。在原生仓库中创建 develop、uat、main，将 uat、main 设为保护分支，配置允许推送的发布人员。保持 Agent 对环境分支无直接写权限。
2. 仓库管理中绑定开发分支和一个实际 Agent 账号，保存编码约束。建议给不同仓库使用独立 Bot 用户，通过原生团队或协作者权限授予该 Bot 对功能分支的读写能力。
3. 用户权限中选择账号和分支。develop 授予「审批列表」及所需审批按钮，uat 或 main 授予「发版页」及所需发布或撤销按钮。同一用户、仓库与分支的设置覆盖保存。通配分支与精确分支取并集。原生仓库权限和保护规则同时生效。业务角色的授权只控制业务工作台，原生界面的权限通过 Gitea 原生设置维护。
4. MCP 授权页生成仓库密钥，客户端连接页面给出的 HTTP 地址并设置 Authorization 标头为 Bearer 加空格和密钥。原生交付 MCP 的 coding_instructions 工具返回目标仓库、开发分支和提示词。编码、Git 推送和创建 PR 使用 Agent 自身账号，可通过既有的 gitea-mcp-server 完成。在 Bot 账号资料维护该外部服务的 Gitea PAT。两个服务的令牌各自轮换与撤销。
5. Agent 向 develop 发起 PR 后，拥有审批权的人可查看具体差异、合并、关闭 PR 或请求专家审查。合并采用仓库默认合并方式，检查 PR 头提交、状态检查、签名与保护规则。业务列表按 Agent 账号、目标分支与当前操作者授权筛选。
6. 发版页根据实际存在且匹配保护规则的分支生成标签，每页 20 条开发主线提交。发版通过 Gitea 原生 cherry-pick 写入目标分支，合并提交按第一父提交取差异。撤销使用目标上的发布提交生成反向提交。工作台通过目标分支提交记录识别自己执行的发布和撤销。分支共有的历史单独标记，原有手工 cherry-pick 记录需在导入前核对。

## 配置服务器推送

1. 在仓库开启 Actions，注册带有 uat、prod 标签的 Runner。任务镜像需要 POSIX shell、curl、OpenSSH 客户端，并能访问 Gitea 和目标主机。
2. 分别在两个环境分支的 .gitea/workflows/ 目录提交 deploy-uat.yml 和 deploy-main.yml。文件名为 deploy-分支名.yml，分支名中的斜杠替换为短横线。自定义分支需同步修改触发规则、部署参数、并发组和 Runner 标签。
3. 从工作台的「部署环境」维护主机地址、部署用户、私钥和已核验的 known_hosts 记录。服务器可为腾讯云 CVM、阿里云 ECS 或内网 Linux，示例使用 SSH 22 端口。Gitea 使用实例 SECRET_KEY 加密保存。只有受保护分支的 push 事件、当前仓库对应名称的部署工作流能获得该环境的 SSH 信息。审核能改动受保护分支工作流的变更。
4. 在目标服务器准备 /usr/local/bin/deploy-revision。它接收环境分支和完整 SHA，从标准输入读取该提交的源码 tar.gz。应用上线和健康检查成功后返回 0，失败返回非零。随包的 deploy-revision 是静态站点示例，要求源码根目录有 index.html。安装脚本并授予执行权限，提前为部署用户创建 /srv/business-site/uat/releases 或 /srv/business-site/main/releases，将 Web 服务指向对应 current 目录。服务端应用替换为自身构建、重启及健康检查逻辑。
5. 发版会在受保护分支产生 push 事件。Runner 领取 Action 后下载指定 SHA 的源码包并通过 SSH 主动推送到环境。发版页分别展示 Git 目标版本和最近成功的部署工作流对应版本。健康检查的质量取决于目标端脚本。部署失败可在 Actions 查看日志，修复后重跑；重新运行历史任务会重新部署该版本，请按环境操作流程控制重跑权限。

## 验收与恢复

- 以站点管理员和普通用户分别登录，检查仓库列表、分支及按钮。访问未授权仓库写操作应被拒绝。
- 以 Agent 提交一个可识别的页面变更，完成审批。在 UAT 发版，确认生产分支指针保持原值；核对目标实际内容、工作流状态和页面的版本。
- 撤销 UAT 发版，确认生成新提交并经过同一条部署流水线。重复提交已打开页面的旧操作应因分支头变化被拒绝。
- 在部署脚本中模拟失败，成功版本应保留上次值。撤销 MCP 密钥后，旧密钥应无法再调用工具。
- 回退应用使用发版撤销。回退 Gitea 本身请还原升级前的数据库、数据卷、配置及匹配版本镜像。

源码构建入口为 make build，工具链要求以 go.mod 和 package.json 为准。自动化权限测试为 go test -run TestDeliveryGrantScope ./routers/web/repo。
